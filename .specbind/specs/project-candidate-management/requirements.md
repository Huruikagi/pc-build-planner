## 背景

<!-- specbind:instruction maintain

利用者が複数のWebページで見つけたPCパーツ候補を、プロジェクトごとに手元で比較・補正しながら検討できるようにする。候補情報は取得の成否や確認状況にかかわらず検討途中の情報として扱い、利用者の判断を置き換えない。

### 対象

- プロジェクトの作成、選択、名称変更および削除
- プロジェクト内の候補の保存、編集および削除
- 不完全、未分類または未確認の候補を含む検討途中の情報の管理
- 自動取得した値、利用者が確認した値および取得元の区別

### 要件 1: プロジェクトの管理

利用者が比較対象となる候補群を目的ごとに分けて管理できるようにする。

#### 受け入れ基準

1. 利用者がプロジェクトを作成したとき、候補を持たないプロジェクトが利用可能になる。
2. 複数のプロジェクトがあるとき、利用者が選択したプロジェクトの候補だけが操作対象として表示される。
3. 利用者がプロジェクト名を変更したとき、そのプロジェクトは新しい名称で識別できる。
4. 利用者がプロジェクトを削除したとき、そのプロジェクトとそのプロジェクトに属する候補は利用できなくなる。
5. プロジェクトが存在しないとき、候補を保存する前に利用者がプロジェクトを作成または選択できる。

### 要件 2: 不完全な候補の保存と補正

取得できた情報が不完全でも、後から利用者が補正できる検討途中の候補として扱う。

#### 受け入れ基準

1. 利用者がURLだけを持つ候補を保存したとき、商品名が未取得でもその候補は選択中のプロジェクトに保存される。
2. 利用者が候補を追加または編集したとき、商品名、分類、価格、URLおよび属性のうち分かっている情報だけを候補に保持できる。
3. 候補の分類、商品名または属性が未入力・未確認のとき、候補は不完全な検討途中の状態として表示され、保存を妨げない。
4. 利用者が保存済み候補を補正したとき、補正した内容が候補に反映される。
5. 利用者が候補を削除したとき、その候補はプロジェクトの候補一覧から利用できなくなる。

### 要件 3: 取得値と確認済み値の区別

利用者が自動取得の推測と自分で確認した情報を区別して判断できるようにする。

#### 受け入れ基準

1. ページなどから取得された候補情報があるとき、利用者は取得された元の値を確認できる。
2. 利用者が候補の値を確認または編集したとき、その値は元の取得値と区別して保持される。
3. 候補に確認済みの値がないとき、利用者はその値が未確認であることを識別できる。
4. 利用者が確認済みの値を変更しても、取得された元の値は利用者が参照できる状態で残る。

### 要件 4: 取得元の管理

候補の情報がどのページまたは入力から得られたかを、利用者が比較と補正に使えるようにする。

#### 受け入れ基準

1. 候補をURLを伴う情報から保存したとき、そのURLを取得元として候補に関連付けられる。
2. 利用者が候補へ取得元を追加、変更または削除したとき、候補に関連付ける取得元を更新できる。
3. 候補に複数の取得元があるとき、利用者はそれらを同じ候補の取得元として確認できる。
4. 取得元がない候補でも、利用者は候補を保存および補正できる。

### 要件 5: 重複候補の利用者選択による統合

重複の可能性を知らせつつ、自動判定だけで利用者の候補を失わせないようにする。

#### 受け入れ基準

1. 新しい候補を保存しようとしたとき、既存候補と重複する可能性がある場合は、利用者がその候補を確認できる。
2. 重複候補が提示されたとき、利用者は新しい候補として保存するか、選択した既存候補へ情報を統合するかを選べる。
3. 利用者が新しい候補として保存することを選んだとき、既存候補を変更せずに新しい候補を保持する。
4. 利用者が既存候補への統合を選んだとき、選択した既存候補へ新しい候補の利用可能な情報と取得元を反映し、新しい候補を別の候補として保存しない。
5. 重複の可能性がないとき、利用者は候補を通常どおり保存できる。
