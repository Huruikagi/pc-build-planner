## ツリーの組織

実行可能な実装は `src/`、実ブラウザで拡張境界を検証するシナリオは `e2e/`、ビルドと配布の
自動化は `scripts/` に置く。利用者向け文言は `_locales/`、仕様と設計の記録は `docs/` に置く。
`salvage/` は旧実装から得た非コンパイルの参照知識であり、新しい実装や検証の配置先にしない。

`src/` 内は責務で分ける。共有データ語彙と永続スキーマを model、機能操作を feature logic、
表示と入力を UI が担い、依存は概ね `model → feature logic → UI` に向ける。保存 adapter は
最小のルート単位 I/O を担い、機能判断を持たない。

## 命名

機能操作は対象となる概念の名前、画面は `*-screen.tsx`、ブラウザ実行境界は役割が分かる名前を
使う。新しい抽象名を増やすより、既存の概念と責務に合わせる。

## 新しい作業の置き場所

- 共有データ形状や保存スキーマは model の所有箇所へ置く。
- 部品、構成、互換性などの操作は、それぞれの feature logic へ置く。
- 画面は既存の `SCREENS` と対応する screen component へ追加し、別の registry や contribution
  機構を作らない。
- ページ抽出、正規化、通信検証は `capture` 境界の該当責務へ置き、UI、保存、サイト固有の
  恒久セレクターを持ち込まない。
- runtime entry を追加する場合は、ソースだけでなく明示的なビルド entry と Manifest も扱う。
- 振る舞いの検証は feature ごとの E2E、架空ページ入力は E2E fixture に置く。

## 例を示す価値のある規約

商品ページの取り込みでは、DOM からの生候補抽出は capture の extractor、未信頼メッセージの
検証は protocol、採否と確認済み値への反映は拡張側の feature logic が担う。この分割により、
ページ側コードが保存や互換性判断へ直接依存しない。
