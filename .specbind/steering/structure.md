## ツリーの組織

新しいコードの置き場所は、最初に実行境界で決め、その中で責務を所有する feature に置く。
拡張の composition root、service worker、ページ抽出、UI、ビルドスクリプト、実ブラウザ E2E は
別の境界である。共有コードは、複数 feature が同じ低レベル責務を必要とするときだけ基盤へ置く。

ドメイン操作は immutable な root transformation としてモデルに依存し、永続化はモデルの
直列化と検証を所有する。UI と抽出は永続化実装へ直接依存せず、抽出側から UI や保存層へも
逆依存しない。

## 命名

ファイル名は所有する概念または feature を表す。画面は `*-screen.tsx`、画面を補助する編集・選択
UI は `*-editor.tsx` や `*-choice.tsx` とする。単なる技術カテゴリより、候補、プロジェクト、現在構成、
互換性など、責務の語彙を優先する。

## 新しい作業の置き場所

1. entrypoint、capture、UI、script、E2E のどの実行境界に属するかを決める。
2. その境界で状態と振る舞いを所有する feature に置く。
3. 複数 feature で同じ責務を共有すると確認できた場合だけ、モデル、ストレージ、国際化などの
   共有基盤へ昇格する。

第二の独立 consumer が存在しないコードを別 package にせず、参照保存用の領域を通常の import 先や
新規実装先にしない。設計履歴を実行時契約の代わりにせず、現在のコードと E2E を正とする。

## 例を示す価値のある規約

ページから部品候補を取り込む変更では、DOM の読み取りと抽出を capture 境界に置き、候補の検証・
採否・保存はそれぞれの owner に渡す。画面から `chrome.storage` を直接呼んだり、content script に
保存判断を持たせたりしない。新しい責務は、似た名前のファイルではなく、この所有関係に従って
配置する。
