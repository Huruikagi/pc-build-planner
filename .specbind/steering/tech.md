## 構成技術

Chrome Manifest V3 拡張として、TypeScript と React で side panel を構成する。service worker と
side panel は ESM、ページへ注入する content script は Chrome の実行境界に合わせて別の IIFE
としてビルドする。Node.js と pnpm の実行環境は mise、依存解決は lockfile で再現する。

## 決定とその理由

- 本番と開発ハーネスは同じ `App` composition を使い、保存と翻訳の adapter だけを差し替える。
  本番と開発で UI の挙動が分岐するのを避けるためである。
- ページ読み取りは拡張アイコンの明示操作時だけ行い、`activeTab` と `scripting` の一時権限で
  content script を注入する。常時監視や過剰な権限を持たせないためである。
- ページ由来のメッセージは未信頼入力として Zod で境界検証する。抽出は生の候補を返すだけにし、
  採否、正規化、確認済み値への昇格をページ側へ持ち込まない。
- 永続化は `chrome.storage.local` の単一キー・単一ルートを使う。読み取り時にスキーマ検証し、
  未初期化は正常、破損は通知対象とする。書込みは直列化して revision を進める。
- 欠損を正常状態として保持し、不確かな値から断定しない。必要性が実証されるまでは、ロック、
  トランザクション runner、自動修復などの複雑な回復機構を追加しない。

## すべての変更が引き継ぐ制約

- runtime entry を増やす変更は、ビルド定義と Manifest の実行境界を同時に扱う。
- content script は抽出と送信に限定し、UI、保存、互換性判断を持たない。
- 自動取得した `original` と利用者が確認した `confirmed` を混同せず、互換性判定には
  `confirmed` だけを使う。
- `dist/` はビルド生成物であり、直接編集しない。
- UI 文言は Chrome の `_locales` を通し、アプリ内独自の言語切替を設けない。

## 検証方法

初回は `pnpm install` を実行し、E2E 用ブラウザがなければ `pnpm install:e2e-browser` を実行する。
標準の一括検証は `pnpm validate` で、lint、型検査、ビルド、Playwright E2E を通す。

検証の正は、ビルド済みの未パッケージ拡張を実 Chromium に読み込む E2E とする。E2E は実際の
`chrome.storage.local` を確認し、日本語と英語のブラウザ UI 言語を分けて実行する。合成した
コンポーネントテストだけで拡張境界の成功を代替しない。
