## 構成技術

Chrome Manifest V3 拡張を TypeScript と React で構築する。service worker と side panel は ESM、
ページへ注入する content script は classic script として成立する IIFE にビルドする。開発ツールの
バージョンはリポジトリで固定し、lockfile を変更せずに CI とリリースを再現できる状態を保つ。

## 決定とその理由

- ページと content script から届く値は未信頼入力として扱う。許可リスト、走査量と文字数の上限、
  スキーマ、完全一致による検証を境界で行い、サイト固有処理や推測に依存しない。対象サイトが
  増えても安全性と説明可能性を保つためである。
- 永続化は `chrome.storage.local` 上の単一 root とし、読み込み時にスキーマ検証して、更新時は
  root 全体を原子的に置換する。複数の writer や部分更新による整合性崩れを避けるためである。
- 取得元の表記と利用者が確認した値を分離する。欠損を正常状態として保持し、互換性判定では
  確認済みの値だけを根拠にすることで、不確かな情報を確定事実として扱わない。
- 単一パッケージを維持し、実在する複数 consumer が生じるまで workspace 分割や先回りした抽象化を
  導入しない。現在の実行境界と所有責務を、配布単位より細かく分断しないためである。

## すべての変更が引き継ぐ制約

- TypeScript の strict 設定と、optional・index access を厳密に扱う設定を弱めない。
- UI、抽出、永続化の境界を越えて Chrome API や未検証入力を漏らさない。
- ストレージ破損は黙って初期化せず検出して通知し、既存データを暗黙に失わない。
- service worker、side panel、content script それぞれの実行形式を保ち、生成物を手編集しない。
- 実需要が確定していないバックアップ、復旧、複雑な transaction 層を前提にしない。

## 検証方法

ローカルの標準検証は `pnpm validate` とする。初回は `pnpm install` で依存関係を導入し、
`pnpm install:e2e-browser` で Playwright の Chromium を準備する。

静的検証は lint、型検査、ビルドの順に行う。利用者フローの正は、ビルド済みの未パッケージ拡張を
実ブラウザへ読み込む Playwright E2E とする。合成コンポーネント用のハーネスを、拡張実行境界を
通る検証の代替にはしない。CI も同じ順序で実行し、E2E 失敗時は追跡可能な成果物を残す。
