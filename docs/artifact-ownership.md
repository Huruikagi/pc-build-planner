# 成果物の所有権と更新フロー

性質の異なる成果物が併存するとき、どれが現行の正で、いつ更新されるかを定める文書。個々の内容そのものは各成果物が持つ。

> [!NOTE]
> 本書は**運用判断の記録**であり、毎セッション読み込まれる steering ではない。エージェントの挙動を変える規約は含まないため、steering へは抜き出していない。

## 原則

**手で維持する Markdown を正にしない。** 正は実装物（コード、デザイントークン、Storybook、テスト）に置き、Markdown は意思決定の記録か、消費済みの入力として凍結する。

自分を正だと宣言した md は、更新トリガが人間の記憶に依存するため必ず陳腐化する（`docs/requirements-v0.1.0.md` の実例）。

## 所有権の一覧

| 成果物 | 所有する情報 | 更新トリガ |
|---|---|---|
| steering | プロジェクト全体の判断基準・規約・制約 | 原則が変わったとき |
| `.kiro/specs/` | feature 単位の要件・設計・意思決定 | 担当ドメインに作業が来たとき（`/kiro-discovery` Path A） |
| コード | 唯一の実行可能な真実 | 常時 |
| デザイントークン | 色・余白・タイポ等のスケールと意味 | 大幅改訂時に確定し、以降は実装コードとして維持 |
| Storybook | 画面とコンポーネントの現況・状態バリエーション | 実装時（story-first） |
| 画面カタログ | 改訂前の現況。デザインAIと discovery への入力 | 採取時のみ。以降は凍結 |
| デザイン仕様 / モック | その改訂で目指す姿。実装前の入力 | 作成時のみ。実装完了後は凍結 |
| `docs/` | 特定バージョン時点の記録、および先送り一覧 | 凍結済み文書は更新しない |

## 凍結境界

デザイン改訂の成果物は、実装に到達した時点で更新をやめる。

```text
実装（現況） ──採取──> 画面カタログ ──> デザインAI ──> UI仕様
                        （docs/）                       ↓
                                      ui-ux steering（原則のみ）
                                                        ↓
                                   /kiro-discovery（spec構成を判定）
                                                        ↓
                                     spec: requirements → design → tasks
                                                        ↓
─────────────── 凍結境界 ───────────────────────────────┼───────────
                                                        ↓
                        実装（story-first）──> Storybook + デザイントークン
                                                    ＝ 以降の正
```

- 境界より上は消費済みの入力であり、実装後は維持しない。
- モックと実装が乖離した場合は実装を正とする。突き合わせの対象にしない。
- 「今どんな画面が何をするか」は Storybook の画面単位ストーリー（loading / error / empty / maintenance を含む）が持つ。同じ情報を md へ二重化しない。
- デザインAIによるモック生成は大幅改訂時（v1.0.0 等）にのみ行う。都度の UI 変更では回さない。
- **画面カタログは spec より前に作る。** 現況の採取であって目指す姿ではなく、spec の境界をどう切るかはカタログと UI 仕様を入力にした `/kiro-discovery` が決める。採取時点のバージョンを記名して `docs/` へ置く。
- テキストの UI 仕様は、spec 構成が決まった後に対応する spec 配下へ置く。画像・Figma 等の外部資産はリポジトリへ取り込まず、参照先と採取日・対象バージョンだけを記録する。

## 改訂間の一貫性

大幅改訂の間に入る UI 変更の一貫性は、実装物だけで担保する。

- **デザイントークン**: 値の定義は共有コアモジュール1箇所が所有し、feature の CSS は参照だけを行う。feature 所有 CSS が持つのは組み方であり、スケールではない。生リテラルの混入は `pnpm validate` の gate で検出する。
- **Storybook**: 共有コンポーネントと状態表示の在庫を可視化する。
- **`ui-ux` steering**: トークンでも story でも表現できない相互作用・アクセシビリティの原則だけを短く持つ。

新規の複合画面の美的判断はこの仕組みでは担保できない。次の大幅改訂でリセットされる前提を受け入れ、md による代替を作らない。

## spec の扱い

spec の更新経路は cc-sdd 側が既に持っている。`/kiro-discovery` が新規 spec・既存 spec の更新・spec 不要を判定し、既存 spec の更新は次の2経路に乗る。

- **Path A**（単一の既存 spec に収まる）: `/kiro-spec-requirements {feature}` で対象 spec を更新する。
- **Path E**（新規 spec と既存 spec 更新の混在）: 既存 spec への拡張を roadmap の `Existing Spec Updates` 欄へ列挙し、そこから各 spec を更新する。

したがって「spec をいつ触るか」を運用ルールとして別途定める必要はない。

決めておくのは、ツールが判断しない一点だけ。

- **実装済み spec の統廃合・分割を行わない。** 統合すると判断の履歴が失われる。境界の見直しは実装前（roadmap 段階）にのみ行う。
- ディレクトリ移動によるアーカイブもしない。相互参照を壊す一方、spec は毎セッション読み込まれないので圧迫の実害がない。
- 後発 spec が先行 spec の設計を無効化した場合の記録方法は定めない。Path A が担当 spec を更新するため、その更新自体が記録になる。

## steering 自体の制約

steering は全セッションで読み込まれるため、短さが機能要件である。

- **「どう判断するか」を書き、「何があるか」は書かない。** 列挙可能な事実（ファイル一覧、spec 一覧、画面一覧）はリポジトリから取得できるので置かない。
- 1ファイル150行以内、全体1000行以内を目安とする。
- 新規ファイルの追加は、既存の圧縮か削除を伴うか、毎セッション必要である理由を示せる場合に限る。
- 詳細は steering ではなく、spec（意思決定）かコード（実行可能な規約）へ置く。

本書自身もこの制約の対象であり、steering ではなく `docs/` に置く。エージェントが毎ターン参照して挙動を変える文書ではなく、人間が扱い方を決めるための判断記録だからである。

_成果物の内容ではなく、どれが正でいつ凍結するかの判断を記録する。_
