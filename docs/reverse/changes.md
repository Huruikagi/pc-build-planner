## C-1. プロジェクト管理をパーツ管理画面から切り出す（確定）

### 現状の問題

パーツ管理画面の上部を、プロジェクトという「入れ物」の CRUD が占有している。

v0.4.0 の実画面（幅 420px）で計測した占有:

```
y=  90  現在のプロジェクト セレクタ      ← 共通スロット
y= 140  [メインPC 2026] [名前を変更] [削除]   ┐
y= 190  新しいプロジェクト名                   ├ 画面上部の約 40% が
y= 230  [_______________] [プロジェクトを作成] ┘  プロジェクト CRUD
y= 270  カテゴリフィルタ（13 チップ、3 行）
y= 400  [パーツを追加]
y= 430  パーツ一覧 ←  本来の主目的がここから
```

問題は 3 つある。

1. **役割の混在**: 「候補を溜めて比較する」という中の作業をする画面に、
   入れ物そのものの生成・改名・破棄が同居している
2. **常設セレクタとの重複**: 現在のプロジェクトを示す表示が、共通スロットの
   セレクタと画面内の表示で二重になっている
3. **主目的の押し下げ**: パーツ一覧に到達するまでに 400px 以上スクロールを消費する。
   取り込み直後の引き渡しでは編集フォームが一覧のさらに下に展開されるため、
   着地点が画面外になる（実測で確認）

### 変更内容

**プロジェクトの CRUD を、共通プロジェクトセレクタ側へ移す。**

- セレクタは既に全画面に常駐しており、プロジェクト同一性が住む正規の場所である
- 入れ物を「選ぶ」場所と「作る・直す・捨てる」場所を一致させる
- パーツ管理画面は候補の一覧・編集だけを担う

セレクタに管理導線（作成 / 名前変更 / 削除）を付ける。
常時展開せず、明示操作で開く形とし、既定の画面高さを消費しない。

**形式はポップオーバーで確定**（デザインキャンバス「6. プロジェクト管理」）。

- セレクタから開き、切替・改名・削除・作成を 1 つの面で完結させる
- 各行にプロジェクト名と候補数・採用数を出し、切り替え先の中身が見えるようにする
- 作成は同じ面の最下段に入力欄と作成ボタンを置く

採らなかった形式:

| 形式 | 却下理由 |
|---|---|
| モーダル | 切替は頻度が高い。全画面を奪うのは操作コストに見合わない |
| インライン展開 | 開閉で下のコンテンツが動き、本文が押し下げられる。C-1 の問題が形を変えて戻る |

### 採らなかった案

| 案 | 却下理由 |
|---|---|
| ナビに 5 つ目のタブ「プロジェクト」を足す | プロジェクト操作は頻度が低く、常設タブは 4 面すべての等価性を崩す。かつセレクタとの二重管理が残る |
| 設定画面に入れる | プロジェクトはデータであって設定ではない。そもそも C-3・C-4 の結果、設定画面自体を持たない |

### 影響範囲

- `screens.md` 1 章の項目 1・2 を削除し、共通セレクタの節へ移す
- `screens.md` 0 章の共通スロットの記述に管理導線を追加する
- プロジェクト未選択時の「続行するにはプロジェクトを選んでください」導線は、
  パーツ管理画面内ではなくセレクタの管理導線を開く形に統一する

## C-2. 併せて直す UX 欠陥（v0.4.0 で実測した不具合）

リバース中に実挙動で確認した明確な欠陥。再実装時に持ち越さない。

### C-2-1. 互換性確認の文言が連結されて読めない（重大）

実際の表示:

```
CPUソケットRyzen 7 9800X3DASUS ROG STRIX B650E-FAM5 / LGA1700規格が一致していません。
```

ルール名・左パーツ名・右パーツ名・値・理由が区切りなしで連結されている。
`compatibility.ts` のカタログには「助詞連結だった箇所を `{side}` パラメータを受ける
完結した文へ再設計する」というコメントが既にあるが、実装に反映されていない。

**対応**: 判定結果はカタログ側で完結した 1 文として定義し、
断片の連結で組み立てない（`features.md` 7 章の原則をここにも適用する）。

### C-2-2. 取得元表記が生 JSON のテキストエリア

パーツ編集フォームの「取得元表記」が `{"name": "SYN GeForce...` という
生 JSON のテキストエリアとして露出している。利用者が編集する前提の UI になっていない。

**対応**: 元表記は項目ごとの読み取り専用表示にする。
編集させる必要があるのは `confirmed` 値だけである。

### C-2-3. 取り込み後の着地点が画面外

取り込み成功後、パーツ編集フォームは既存パーツ一覧の**下**に展開される。
候補が 3 件あるだけで、フォームは初期表示位置から 1,100px 以上下になる（実測）。
取り込み直後という最も重要な瞬間に、利用者は何も見えない状態から始まる。

**対応**: 編集フォームは一覧の下ではなく、一覧を置き換える形か、
上部に展開する形にする。C-1 と併せると初期位置がさらに改善する。

### C-2-4. パーツカードの情報密度

カードが「カテゴリ / メーカー / 型番 / 価格 / プライマリ」を常に 5 行で表示し、
すべて「未入力」でも 5 行を占める。候補 3 件で 1 画面を使い切る。

**対応**: 未入力項目は畳み、「未入力の項目があります」の 1 行に集約する。
比較のために溜める道具である以上、一覧性は機能要件に近い。

**確定**（デザインキャンバス「1. パーツ管理」）。カード形式をやめ、
1 パーツ 1 行の表形式にする。商品名とメーカー・カテゴリを左に積み、
規格と価格を右の固定幅列で揃える。未入力の項目は行に出さない。
1 画面に 8 件と合計金額が収まる（v0.4.0 は 3 件で画面を使い切っていた）。

### C-2-5. ナビゲーションがアイコンのみで意味が通らない

v0.4.0 のナビは 4 つのアイコンだけで、ラベルは `aria-label` にしかない。
実際に互換性確認のアイコン（パズル 1 ピースの線画）が
パズルとして認識されなかった。14px では凹凸が潰れて形が読めない。

**対応**: 2 点。

1. **ナビはアイコン + ラベルを併記する**。アイコン単独に意味を持たせない
2. **互換性アイコンを「2 ピースが噛み合う」形に変える**。
   「2 つが合うかどうか」という機能そのものを表し、
   2 ピースを `currentColor` + `opacity: 0.45` で塗り分けるので
   14px でも境目が残る（線画は潰れる）

## C-3. バックアップ・復元を機能ごと落とす（確定）

### 決定

v0.4.0 が持っていたバックアップ・復元機能を、再実装では**実装しない**。

### 理由

- ユースケース上、退避と復元の必要性が実感として無い
- 実装・検証コストに見合わない（v0.4.0 では交換形式の検証、容量ポリシー、
  復元後の後処理、回復モード、未保存編集との調停まで抱えていた）
- データ喪失は許容する。拡張削除や破損でデータが飛ぶことを受け入れる

### 影響

| 文書 | 変更 |
|---|---|
| `requirements.md` | 課題 R6 と要求 R-5 を削除。非機能要求に「データ喪失は許容」を追加。対象外へ明記 |
| `screens.md` | 設定画面はバックアップ節を削除し、表示言語のみ |
| `features.md` | 7 章「バックアップ・復元」を削除。破損時の復旧手段を持たないことを明記 |

### 残る責務

破損検出そのものは残す。復旧できなくても、
**壊れたデータを黙って使わない・既存データを上書きしない・利用者へ知らせる**
ところまでは持つ。

## C-4. i18n を Chrome 標準機構へ寄せる（確定）

### 決定

独自のメッセージカタログ・文言解決機構を捨て、
**Chrome 拡張標準の `_locales` + `chrome.i18n` だけを使う。**
併せて、アプリ内の表示言語切り替えを廃止する。

### 現状のコスト

v0.4.0 では `_locales/` は拡張名と説明の 2 キーしか持たず、
UI 文言はすべて独自カタログ側にあった。

| | 行数 |
|---|---|
| `src/ui-messages/` | 1,897 |
| `src/ui-language/` | 409 |
| `tests/ui-messages/` | 1,173 |
| `tests/ui-language/` | 528 |
| **計** | **4,007** |

これが `_locales/{ja,en}/messages.json` の 2 ファイルに置き換わる。

### 独自実装の根拠が成り立たないこと

独自実装は E2E で言語を検証する都合とされていたが、
Chrome 標準機構でも検証できることを v0.4.0 のビルドで実測確認した。

```
--lang=ja     -> uiLanguage "ja",    _locales/ja を解決
--lang=en-US  -> uiLanguage "en-US", _locales/en を解決
```

E2E は `--lang` を変えた 2 コンテキストで同一シナリオを流せばよい。
アプリ内トグルも合成ハーネスも要らない。

### 表示言語切り替えの廃止

`chrome.i18n` はブラウザの UI 言語を見るもので、拡張内から実行時に切り替える API がない。
アプリ内切り替えを維持するには `messages.json` を自前で fetch して差し替える経路が必要になり、
manifest 側の `__MSG_` 置換と 2 系統を抱えることになる。

個人利用でブラウザ言語と表示言語が食い違う場面が実質ないため、**切り替えを廃止する**。

### 影響

C-3（バックアップ廃止）と併せて、**設定画面に残る項目がゼロになる**。

| | v0.4.0 | 再実装 |
|---|---|---|
| 常設ナビゲーション | 4 面（パーツ管理 / 現在構成 / 互換性確認 / 設定） | **3 面**（設定を廃止） |

| 文書 | 変更 |
|---|---|
| `requirements.md` | R-5 をブラウザ言語追従に変更。対象外へ「アプリ内の表示言語切り替え」を明記 |
| `screens.md` | ナビを 3 面に。設定画面の節を削除 |
| `features.md` | 7 章を Chrome 標準機構ベースへ全面書き換え |
