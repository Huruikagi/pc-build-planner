# サイト固有抽出を作成する

この Skill は開発用であり、利用者の Capture 操作を開始しない。代表URLごとに対象サイトの公式な利用条件を探索し、確認結果を新しい `decision.md` に保存してから、開発者が指定した一つのページ URL だけを扱う。明確な禁止根拠がない限り、利用条件の未発見、不明、曖昧さを理由に閲覧、自作の抽出ルール、架空fixture、自動検証、確認用ビルドとリンク集、実サイト手動確認を止めない。実ページ資料の保存は任意であり、保存に適用する条件を確認できない場合は保存しなかった事実を記録して省略する。

## 代表URLから収集を始める

必須入力は、対象ページの代表URLだけである。URLが空、無効、または対象ページを指さない場合だけ、`入力確認` の停止結果を返す。製品カテゴリと取得したい項目が同時に指定された場合は、対象を判断する根拠として使う。未指定であることを理由に停止したり、一つずつ入力を求めたりしてはならない。

利用条件の確認後に利用できる対象ページの資料から、次を根拠とともに区別する。

1. 既存の製品カテゴリのうち、資料が一意に示すカテゴリ
2. 共通項目のうち、資料に明記され、直接読める項目
3. 確定したカテゴリに既に定義された属性のうち、資料に明記され、直接読める項目
4. 資料に明記されない共通項目または属性

カテゴリ、対象項目、アクセス、または製品情報の根拠を自力で確定できないときだけ、候補を作る前に次の三項目をまとめて返す。値、カテゴリ、項目を推測して補ってはならない。

1. 確認済み範囲: 確認できた対象ページ、カテゴリ候補、直接読める共通項目または既存属性
2. 未解決の理由: 一意に確定できないカテゴリまたは項目、アクセス制限、または不足する製品根拠
3. 必要な確認: 未解決のすべてを確定するために開発者が確認または指定する情報

ページ本文、HTML、画像、商品値、認証情報をGit管理対象のリポジトリ、判断記録、Skill の出力へ書き込まない。判断記録には、それらの内容の代わりに資料のローカル識別子だけを記す。

## ローカル作業単位を作る

利用条件の探索結果を整理した後、ライブページを扱う前に、リポジトリ直下のGit管理対象外領域 `/.site-extraction-work/` に実行専用の作業単位を作る。Skill はページ資料と作業記録をこの領域以外へ書き込まず、CI、クリーン環境、別環境への同期や再現を要求しない。

作業単位のパスは `/.site-extraction-work/<host>/<url-hash>/<run>/` とする。`host` は正規化URLの小文字ホスト名で、Windowsで使えない文字を `-` に置換したディレクトリ名にする。`url-hash` は正規化URLをUTF-8でSHA-256化した小文字16進表現、`run` はUTC実行時刻を `yyyyMMddTHHmmssfffZ` 形式にした値とする。対象と実行をこの三要素で区別し、同一対象の以前の実行を上書きしない。

作業単位には用途ごとに次のファイルを分けて残す。

- `page.html`: 保存条件を確認した場合だけ保存する実ページ資料
- `decision.md`: 利用条件の探索で確認した事実、対象作業への解釈、不明点、継続または停止の判断、根拠 URL、確認日、対象 URL、資料識別子
- `candidate.md`: 抽出候補と、候補を登録対象にできるかの結果
- `verification.md`: 保存資料の照合と実拡張検証の結果

作成前に最終パスの不在を確認する。既存の同名作業単位がある、作業領域を作れない、または `decision.md` の保存に失敗したときは停止し、既存の作業単位を変更、上書き、自動削除しない。失敗時の部分的な新規単位も削除せずに残し、候補、検証、登録または既存登録の更新を開始しない。`page.html` の保存は保存条件を確認した場合だけ試み、失敗時は候補、検証、登録または既存登録の更新を進めず、既存または部分作成済みの単位を変更しない。`candidate.md` と `verification.md` は各後続段階の開始時に同じ単位内へ新規作成し、保存失敗時は同じ停止規則に従う。

以前の作業単位を再利用、上書き、または削除して再実装・再生成してはならない。毎回新しい作業単位を作る。作業領域または以前の単位が失われた場合は、以前の判断を流用せず、利用条件を改めて探索して結果を新しい `decision.md` に記録した後に、新しい単位で続行する。

## 実ページの閲覧と任意保存

代表URLからの収集と利用条件の探索を終えた後、明確な禁止根拠が閲覧に適用されなければ、対象ページ URL を確認できる。確認より先に新しい作業単位を作り、同じ単位の `decision.md` へ対象ページ URL、収集または指定で確定した製品カテゴリ、収集または指定で確定した取得したい項目、根拠 URL、確認日、確認した事実、対象作業への解釈、不明点、作業ごとの継続または停止判断を保存する。ページ本文、HTML、画像、商品値、認証情報はこの判断記録へ書かない。

`decision.md` の保存に成功した後、実ページ資料を保存する場合だけ、保存・転載に適用する条件を閲覧条件と別に確認する。保存が明確に禁止される、または保存に適用する条件を確認できない場合は、`decision.md` に保存しなかった事実、根拠または不明点、保存を省略する判断を記録し、`page.html` を作らない。これは閲覧、自作の抽出ルール、架空fixture、自動検証、確認用ビルドとリンク集、実サイト手動確認を停止する理由にしない。保存条件を確認できる場合だけ、同じ単位の `page.html` へ新規保存する。取得または `page.html` の保存に失敗した場合は、候補、検証、登録、既存登録の更新を出さず、既存または部分作成済みの単位を変更、上書き、自動削除しない。停止結果の四項目で、失敗した段階と再試行に必要な対象ページ URL または保存可能な作業領域を示す。

作業領域または以前の作業単位が失われたときも、以前の判断記録、ページ資料、候補、検証結果を読んだり流用したりしない。代表URLから必要情報と利用条件を改めて探索し、新しい `decision.md` にその結果、根拠 URL、確認日を記録できた後に、新しい単位で続行する。

## 停止結果の形式

停止時は、次の四項目だけをこの順で示す。候補、selector、ページ資料の内容、商品値、認証情報を含めない。

1. 対象
2. 停止段階
3. 理由
4. 次に必要なもの

停止結果は次の条件で返す。

| 停止段階 | 対象 | 理由 | 次に必要なもの |
| --- | --- | --- | --- |
| 入力確認 | 欠けた、空の、無効な、または対象ページを指さない代表URL | 唯一の必須入力である代表URLを確認できない | 有効な対象ページの代表URL |
| 保存資料の読取 | 指定された保存済みページ資料のローカルパス | ファイルを読めない、またはページ資料として扱えない | 読み取れる保存済みページ資料のローカルパス |
| ページ識別 | 対象ページ URL と保存済みページ資料 | 資料から対象ページを一意に識別できない | 対象ページを識別できる URL と対応する保存済みページ資料 |
| 要求項目の確認 | 取得したい項目 | 資料に指定項目が明記されず、検出できない | 当該項目が明記された保存済みページ資料、または取得したい項目の見直し |
| ローカル作業領域 | 新規作業単位または開発者指定 URL | 作業単位、判断記録、取得、またはページ保存を完了できない | 保存可能な作業領域、または再取得できる対象ページ URL |

保存資料の読取、ページ識別、要求項目の確認は、利用条件の探索結果と作業ごとの判断を `decision.md` に記録した後だけに行う。明確な禁止根拠が当該作業に適用されるときだけ、その作業と依存する後続を停止する。利用条件の未発見、不明、曖昧さ、または実ページ資料の保存を省略したことだけを理由に、候補作成を停止してはならない。

## この段階の境界

この入力確認を通っても、登録可能な抽出候補はまだ出さない。利用条件の判定、保存資料からの候補生成、検証、`page-capture` への登録または更新、再生成時の既存登録の扱いは、それぞれ後続の手順でのみ行う。

## 利用条件を探索して作業ごとに判断する

入力確認を通過した後、保存済みページ資料を読んだり候補を作ったりする前に、対象サイトの公式な利用条件を探索し、確認に必要なページを閲覧する。開発者に根拠URLや確認日を用意させず、見つからない、読めない、曖昧、または適用が不明だった事実もそのまま扱う。見つからなかった規約、読めなかった内容、許可、根拠URL、確認日を捏造してはならない。

新しい作業単位の `decision.md` には、対象ページ URL、製品カテゴリ、取得したい項目、確認日、根拠URLまたは確認できなかった事実を残し、次を別々に記録する。ページ本文、HTML、画像、商品値、認証情報は書かない。

- 確認した事実: 公式な利用条件の探索範囲、確認できた根拠と、確認できなかった事実
- 対象作業への解釈: 代表ページの閲覧、自作の抽出ルールと架空fixture、自動検証、確認用ビルドとリンク集、実サイト手動確認、任意の実ページ資料保存への適用
- 不明点: 記述の曖昧さ、適用の不明、または保存条件を確認できなかった点
- 判断: 作業ごとの `継続`、または明確な禁止根拠と依存関係による `停止`

### 明確な禁止

今回行う作業に適用される明確な禁止根拠を確認したときだけ、その作業と、その作業を必要とする後続を停止する。停止結果は次の四項目だけをこの順で返し、根拠URL、該当箇所の安全な識別、対象作業への適用理由を理由に示す。

1. 対象
2. 停止段階: 利用条件の判定
3. 理由
4. 次に必要なもの

一部の行為への禁止を、根拠なくすべての作業へ広げてはならない。停止結果には候補、selector、保存済みページ資料の内容、商品値、認証情報を含めない。

### 明確な禁止がない場合と任意保存

利用条件が未発見、不明、曖昧、または対象作業への適用が不明でも、明確な禁止根拠がなければ、確認範囲と不明点を記録して今回の作業を継続する。この継続はサイトから明示的な許可を得たことや適法性を保証するものではない。

実ページ資料の保存は閲覧と別の任意作業である。保存に適用する条件を確認できない、または保存だけが明確に禁止される場合は、`decision.md` に保存しなかった事実、根拠または不明点、保存を省略した判断を記録し、`page.html` を作らない。閲覧、自作の抽出ルール、架空fixture、自動検証、確認用ビルドとリンク集、実サイト手動確認は継続する。保存条件を確認できる場合だけ、実ページ資料を保存できる。

`decision.md` の保存に失敗したときは、既存または部分作成済みの単位を変更せず、候補、検証、登録、既存登録の更新を開始しない。

## 保存済み資料から候補を作る

この手順は、利用条件の探索結果と作業ごとの判断を記録した後に行う。指定した保存済みページ資料を使う場合は、対象ページ URL と対応するページであることを URL または資料中の識別情報から一意に確認する。実ページ資料を保存しなかった場合も、閲覧で確認した構造を基に自作の抽出ルールと架空fixtureによる候補作成・検証を進められる。確認できないときは、`ページ識別` の停止結果を返し、候補、selector、期待値、登録対象を出さない。

ページを識別できたときは、取得したい各項目について、資料に明記された値を直接読む選択規則を一つずつ探す。候補には、次のすべてをそろえる。

- ページ識別条件
- 項目名と選択規則
- 安定した人間可読の由来ラベル
- 資料から検出した未加工の期待値

期待値は選択規則がその資料から読む値との照合にだけ使う。ページ本文、HTML、画像、商品値、認証情報を判断記録または Skill の報告へ転記してはならない。

要求項目の一つでも資料から検出できない、または選択規則で直接読めないときは、候補全体を登録対象にしない。`要求項目の確認` の停止結果で、検出できなかった項目と理由、次に必要な資料または要求項目の見直しを示す。同じ作業単位の `decision.md` に `停止段階: 要求項目の確認`、`対象`、`停止理由`、`次に必要なもの`、`登録結果: 未登録` を残す。この停止結果に候補、selector、期待値、登録対象を含めない。

### 受け付ける項目

候補にできる共通項目は、名称、メーカー、型番、カテゴリ、価格、URLだけである。属性は、対象カテゴリに既に定義された `CATEGORY_ATTRIBUTES` のキーだけを受け付ける。許可する組合せは次に限る。

| 対象カテゴリ | 属性キー |
| --- | --- |
| CPU、マザーボード | `socket` |
| CPUクーラー | `supportedSockets` |
| マザーボード、メモリー | `memoryStandard` |
| マザーボード、電源 | `formFactor` |
| ケース | `supportedMotherboardFormFactors`、`supportedPowerSupplyFormFactors` |

GPU、ストレージ、ケースファンの属性、容量、定格出力、ファン寸法、未分類の属性、既存の `CaptureField` にない属性は候補に含めない。対象カテゴリに対応しない属性キー、または資料に明記されない値も、共通項目への代替や値の推測をせず、候補全体を登録対象にしない。いずれかがあるときは `候補の適合確認` で停止し、同じ作業単位の `decision.md` に `停止段階: 候補の適合確認`、`対象`、`停止理由`、`次に必要なもの`、`登録結果: 未登録` を残す。未対応属性では対象カテゴリに既に定義された属性キーを、未明記値では値が明記された保存済みページ資料を、次に必要なものとして示す。候補、selector、期待値、登録対象は出さない。

この段階で出す候補は未検証であり、登録、既存登録の更新、実行時型や候補編集への引渡しを行わない。保存済み資料による検証と登録の提案は後続の手順でのみ行う。

## 段階的な登録簿差分と候補を引き渡す

代表URLを扱うために登録が不足するときだけ、対象ページで根拠を確認したメーカー、公式ドメイン、既存カテゴリを `MANUFACTURER_DOMAIN_ENTRIES` と照合する。カテゴリまたはメーカーを一意に決められない場合は、登録簿差分を作らず、`確認済み範囲`、`未解決の理由`、`必要な確認` を返す。決められる場合は、同じ組に限る最小の追加または既存エントリの必要最小限の更新を、削除・置換・対象外への展開なしに作る。別のドメインまたはカテゴリ対応表を作らない。

`validated-site-extraction-registration` の第一段階は、未検証の仮適用入力である。候補の同じ安定した識別子に、最小の登録簿差分、ページ識別条件、共通項目と既存カテゴリ属性だけを読む固有規則、実在のHTML・本文・画像・商品値を複製しない架空fixture、固有規則が適用できないときの汎用抽出フォールバックを一組として結び付ける。未明記値、新しい属性、確認済み値をこの一組へ補ったり出力したりしてはならない。

この第一段階の一組は、`page-capture` が所有する候補専用の実拡張E2E構成だけへ仮適用して渡す。本番の `MANUFACTURER_DOMAIN_ENTRIES`、登録簿から選ぶ実行時対象、登録簿以外の実行時選択、未確認handoffの所有を変更しない。`page-capture` から、対象項目と `site-specific` 由来、未確認handoff、固有規則が値を返さない場合の既存汎用フォールバック、候補追加前の既存汎用シナリオ、`pnpm validate` の結果を同じ識別子で受け取る。仮適用は対応済み、実サイト検証済み、または登録可能を意味しない。

第二段階では、保存資料照合、上記の候補専用E2E、既存汎用シナリオ、`pnpm validate` がすべて合格した同じ一組だけを登録可能な入力として `page-capture` へ引き渡す。合格前の候補、いずれかの失敗結果、または異なる差分から登録可能な入力を作ってはならない。登録簿への反映、実行時選択、未確認handoffの実装と所有は、引渡し後も `page-capture` に残る。

## 検証済み候補の登録と候補編集への引渡しを提案する

保存済み資料で、候補の各期待未加工値と指定項目ごとの selector が直接読んだ未加工値がすべて一致すると確認しても、それは中間的な照合合格にすぎない。全項目一致なら `verification.md` に `照合: 全項目一致`、`保存資料照合結果: 合格（実拡張検証待ち）`、`登録結果: 未登録` を残す。ここでは `検証結果: 合格`、`実拡張検証結果: 合格`、`登録結果: 登録可能な候補を提案` を記録せず、登録差分、更新提案、または候補編集への引渡しも出さない。一項目でも読取不能、不足、または不一致なら、同じ `verification.md` に対象項目と安全な失敗理由、`検証結果: 不合格`、`登録結果: 未登録` だけを残して停止する。どちらの場合も `decision.md` には利用条件の判断だけを残し、保存資料照合または登録結果を追記しない。`page-capture` 所有の実拡張検証と `pnpm validate` を含む後段の全条件が合格した後だけ、第一段階の同じ識別子・同じ差分を登録または更新として提案できる。この提案には、追加または更新する `src/capture/site-extractors.ts` のサイトごとの登録、対象カテゴリ、ページ識別条件、項目ごとの selector、変換しない未加工の読取規則、安定した人間可読の由来ラベルを含める。抽出元タイプは `MANUFACTURER_DOMAIN_ENTRIES` を唯一の正本として、登録済みエントリのドメイン、カテゴリ、ページ識別条件から静的に選び、同じエントリに属する fixture、固有規則、失敗時の汎用フォールバックと一組で提案する。

登録提案は、`page-capture` が所有する次の実行時変更を一組として明示する。

- `SiteExtractor` の collector が `RawCandidate` を返し、`field` は既存の `CaptureField`、`rawValue` は selector が得た未加工の文字列だけにすること
- `ExtractionSource` と protocol の列挙に固定値 `site-specific` を追加し、`source` に動的なサイト名や selector を入れず、`sourceLabel` に安定した由来ラベルを入れること
- `captureSource_site_specific` の日本語・英語メッセージを追加し、既存の `captureSource_${source}` と項目由来表示で利用者に固有由来と `sourceLabel` を示すこと

固有規則は、登録簿から静的に選んだ抽出元タイプの許可ホストとページ識別条件に一致するときだけ適用する。selector が見つからない、または読取中に失敗した項目は候補を追加せず、例外を外へ出さない。その後も既存の JSON-LD、meta、構造 collector を実行して、その項目を汎用抽出へフォールバックさせる。この登録簿に基づく静的選択、固有由来、失敗時の汎用フォールバック、同一項目では既存の先着規則により固有候補が選ばれることを、登録提案の検証対象に含める。

候補編集への引渡しは、`page-capture` が consume する `candidate-capture-handoff` だけを使うよう提案する。完全な handoff には、名称・メーカー・型番の元表記、取得時分類の元表記と対応する既存 `PartCategory`、そのカテゴリの `CATEGORY_ATTRIBUTES` にある属性キーごとの元表記、URL、取得元種別、取得時刻、任意の価格を含める。由来ラベルは登録規則と実拡張検証の証跡に限り、handoff、候補の永続データ、確認済み値へ渡したり保存したりしない。分類が得られない場合は属性を渡さない。既存属性を扱う提案では、許可されたキーだけが属性元表記として渡り、分類・属性の元表記は候補編集で未確認のままであり、利用者が確認するまで `category` または属性の `confirmed` へ昇格しないことを検証対象に含める。

この Skill は `page-capture` の実行時型、Zod 検証、正規化、session 結果、または `project-candidate-management` の handoff 型、候補下書き、保存、確認済み値への昇格を実装・所有しない。これらの変更と実拡張での検証は各所有者へ提案するだけであり、登録提案そのものは後続の保存資料および実拡張の検証に合格するまで実行しない。

## 実拡張で登録候補を検証する

保存済み資料の検証を通った候補であっても、この段階を完了するまで登録または更新を提案してはならない。`page-capture` が所有する `e2e/capture.spec.ts` の既存入口を拡張し、ビルド済み拡張を起動して確認する。新しいテスト基盤や実サイト由来の資料は作らない。

1. 候補を追加する前に、同じ実在データを含まない fixture で既存の汎用抽出シナリオを実拡張から実行し、その安全なシナリオ識別子と結果を `verification.md` に控える。ページ本文、HTML、商品値、selector、認証情報は控えない。
2. 候補を加えた検証では、拡張アイコン操作を入口として、指定項目の `site-specific` 由来と安定した `sourceLabel`、`CaptureResult` と候補編集に渡る分類・属性の未確認性を確認する。属性を扱う場合は、対象カテゴリの許可キーだけが元表記として handoff へ渡り、由来ラベルが handoff、候補の永続データ、確認済み値にないこと、`category` と属性の `confirmed` が設定されないことも確認する。
3. 同じ fixture で固有 selector が値を返さない状態を作り、例外を外へ出さず、その項目が JSON-LD、meta、構造 collector による既存の汎用結果へフォールバックすることを確認する。資料に明記されない項目は候補にも handoff にも加えず、推測しない。
4. `pnpm validate` を実行し、前段で記録した汎用シナリオを含む既存シナリオが維持されることを確認する。実拡張の観測、指定項目の保存資料による検証、汎用シナリオの維持のすべてに合格したときだけ、`verification.md` に `実拡張検証結果: 合格` と `登録結果: 登録可能な候補を提案` を残して登録または更新の提案を出す。いずれかが失敗した場合は同じ `verification.md` に `登録結果: 未登録` を残して停止し、登録差分や更新提案を出さない。

fixture、E2E、実行時変更は `page-capture` の所有物である。この Skill は、実在のサイト、URL、ページ資料、商品値を作らず、登録候補ごとに上記の検証を所有者へ提案するだけにする。固定 Skill 手順の照合は `references/verification.md` に従い、実拡張 E2E で置き換えない。

## 確認用成果物を引き渡し、実サイト手動確認を記録する

保存資料照合、`page-capture` 所有の実拡張E2E、`pnpm validate` がすべて合格した候補だけに、同じ作業単位で確認用成果物を用意する。確認用ビルドは `page-capture` が作成・識別するビルドを使い、リンク集HTMLには代表URL、対象カテゴリ、確認項目、拡張を操作して結果を確認する手順だけを記す。リンク集は通常のリンクだけを提供し、リンク先の本文または画像を埋め込まず、リンク先を自動で開いたり巡回したりしない。実サイトのURL、ページ資料、商品値、selectorをGit管理対象のファイルへ転記しない。

この引渡しの時点では `verification.md` に `状態: 自動検証済み・実サイト未確認`、確認用ビルドの安全な識別子、リンク集の安全な識別子、代表URL、対象カテゴリ、確認項目、引渡し日時を残す。これは実サイト対応済み、実サイト手動確認の成功、または最終実装検証の合格を意味しない。自動E2E、汎用フォールバック、または `pnpm validate` のいずれかが失敗した候補は、確認用成果物を作らず、`verification.md` に安全な失敗した確認項目、`実拡張検証結果: 不合格`、`登録結果: 未登録` を残し、検証済みとして扱わない。

開発者が実サイトを確認した後、同じ `verification.md` に対象URL、確認用ビルドの安全な識別子、確認日時、項目ごとの `成功`、`不一致`、または `未確認`、不一致なら安全な実際の結果を対応付けて残す。必要な項目が一つでも `未確認` なら状態は `MANUAL_VERIFY_REQUIRED` とし、実サイト対応の完了を認定しない。すべて成功したときだけ `実サイト手動確認: 成功` を記録できる。不一致が一つでもあれば `実サイト手動確認: 不一致` と `検証結果: 不合格` を記録して修正または再生成へ戻し、未確認候補を既存の検証済み登録へ置換しない。最終実装検証の判定はこの記録を消費する後続の検証であり、このSkillは実サイト確認を自動実行しない。

## 再生成時に既存登録を保持する

再生成は代表URLから開始する。自動E2Eまたは実サイト手動確認の不一致を再生成が必要な結果として扱い、そのURLに対応する既存の検証済み登録、既存登録の安全な識別子、および利用できるローカル記録を自ら探索する。一意に見つかった識別子や保存場所を開発者へ再入力させず、利用できない記録は流用しない。代表URLが有効なら、初回と同じく必要情報と利用条件を改めて探索し、確認した事実、対象作業への解釈、不明点、作業ごとの継続または停止判断、根拠 URL、確認日を新しい作業単位の `decision.md` に記録する。保存資料を使う場合は新しい保存資料に既存登録を照合し、保存しない場合は自作の抽出ルールと架空fixtureによる検証へ進める。指定項目のいずれかを直接読めない、または期待値と一致しないときは、その安全な識別子だけを再生成対象として示す。この判定は既存登録の更新、削除、または未確認候補への置換を行わない。

明確な禁止根拠があるときは、対象作業と依存する後続だけを停止する。既存の固有規則の実行だけが明確に禁止され、汎用抽出には明確な禁止が適用されない場合、既存のコードと検証済み状態を保持したまま、静的な選択状態を `suppressed` にして固有規則を選ばないことと、汎用抽出へのフォールバックだけを `page-capture` へ提案する。汎用抽出にも明確な禁止が適用される場合は、Capture とその依存後続を停止し、汎用フォールバックを提案しない。禁止根拠の適用が不明なだけの場合は、不明点と作業ごとの継続判断を記録して続行する。いずれの場合も、実行時の `page-capture` は事前に決めた静的な選択抑止とフォールバックだけを消費し、利用条件、作業領域、判断記録を読んだり再判定したりしない。

探索結果を記録した後、候補生成、保存資料を使う場合の指定項目の確認、候補追加前の汎用シナリオ記録、実拡張検証、`pnpm validate`、必要な実サイト手動確認を初回と同じように順に繰り返す。候補生成中に要求項目の欠損または候補の適合失敗があった場合は、初回と同じく新しい `decision.md` にその停止段階、対象、停止理由、次に必要なもの、`既存登録: 保持`、`登録結果: 未登録` を記録する。保存資料照合、実拡張検証、`pnpm validate`、または実サイト手動確認で失敗した場合は、新しい `verification.md` に `再生成日時`、保存資料を使った場合だけ `保存資料識別子`、`既存登録: 保持`、`失敗段階`、`停止理由`、`次に必要なもの`、`検証結果: 不合格`、`登録結果: 未登録` を記録する。どの失敗でも既存の検証済み登録を保持し、`decision.md` または `verification.md` の記録先以外へ失敗理由を重複記録せず、既存登録の差分、未確認候補による置換、登録または更新の提案を出してはならない。

新しい保存資料の指定項目検証と実拡張検証がともに合格し、既存の汎用シナリオも維持された場合だけ、既存登録を更新できる候補として提案する。この提案は既存登録を直ちに置き換える操作ではない。
