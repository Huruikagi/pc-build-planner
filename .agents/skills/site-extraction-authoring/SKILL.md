# サイト固有抽出を作成する

この Skill は開発用であり、利用者の Capture 操作、実サイトへのアクセス、ページ資料の取得を開始しない。対象は開発者が指定した一つのページだけである。

## 最初に確認する入力

次の入力を、順序を変えずに一つずつ確認する。各入力が明示され、有効だと確認できるまで、次の入力やページ資料の内容を扱わない。

1. 対象ページ URL
2. 製品カテゴリ
3. 取得したい項目
4. 保存済みページ資料のローカルパス
5. 判断記録のローカル出力先

判断記録の出力先は、開発者が明示したリポジトリ外のローカルパスだけを受け入れる。リポジトリ内のパス、未指定の既定パス、リポジトリ外か確認できないパスは受け入れない。ページ本文、HTML、画像、商品値、認証情報をリポジトリ、判断記録、Skill の出力へ書き込まない。判断記録には、それらの内容の代わりに資料のローカル識別子だけを記す。

いずれかの入力が欠ける、空である、またはこの制約を満たさない場合は、そこで停止する。登録可能な抽出候補、コード変更、検証、登録を出してはならない。

## 停止結果の形式

停止時は、次の四項目だけをこの順で示す。候補、selector、ページ資料の内容、商品値、認証情報を含めない。

1. 対象
2. 停止段階
3. 理由
4. 次に必要なもの

停止結果は次の条件で返す。

| 停止段階 | 対象 | 理由 | 次に必要なもの |
| --- | --- | --- | --- |
| 入力確認 | 欠けた、空の、または制約に合わない入力 | 固定順の必須入力を確認できない | 該当する入力。判断記録の出力先なら、リポジトリ外であることを確認できる開発者指定のローカルパス |
| 保存資料の読取 | 指定された保存済みページ資料のローカルパス | ファイルを読めない、またはページ資料として扱えない | 読み取れる保存済みページ資料のローカルパス |
| ページ識別 | 対象ページ URL と保存済みページ資料 | 資料から対象ページを一意に識別できない | 対象ページを識別できる URL と対応する保存済みページ資料 |
| 要求項目の確認 | 取得したい項目 | 資料に指定項目が明記されず、検出できない | 当該項目が明記された保存済みページ資料、または取得したい項目の見直し |

保存資料の読取、ページ識別、要求項目の確認は、利用条件の判定が許可となった後だけに行う。利用条件が禁止または判断不能のときの停止と判断記録は、この Skill の後続の規約判断手順に従う。ここで保存資料を読んだり、候補を作ったりしてはならない。

## この段階の境界

この入力確認を通っても、登録可能な抽出候補はまだ出さない。利用条件の判定、保存資料からの候補生成、検証、`page-capture` への登録または更新、再生成時の既存登録の扱いは、それぞれ後続の手順でのみ行う。

## 利用条件を判定する

入力確認を通過した後、保存済みページ資料を読んだり、ファイルの内容を確認したりする前に、対象サイトの利用条件を判定する。この Skill は実サイトへアクセスしないため、開発者が示した利用条件の根拠 URL と確認日だけを判定根拠として扱う。根拠が抽出作成を許可することを明示できるときは `許可`、禁止するときは `禁止`、どちらとも確認できないときは `判断不能` とする。推測で `許可` にしてはならない。

判断ごとに、開発者が指定した判断記録の出力先へ、対象ページ URL、製品カテゴリ、取得したい項目、保存済みページ資料のローカル識別子、判断（`許可`、`禁止`、または `判断不能`）、根拠 URL、確認日を記録する。判断記録にはページ本文、HTML、画像、商品値、認証情報を書かない。

### 禁止または判断不能

判断が `禁止` または `判断不能` なら、同じ判断記録に停止理由と次に必要な確認を記録して、直ちに停止する。保存済みページ資料の読取、候補生成、検証、登録、既存登録の更新を開始してはならない。停止結果は次の四項目だけをこの順で返す。

1. 対象: 対象サイトの利用条件
2. 停止段階: 利用条件の判定
3. 理由: `禁止` なら抽出作成を許可しない根拠、`判断不能` なら許可または禁止を確認できない根拠
4. 次に必要なもの: `禁止` なら抽出作成を許可する明示的な根拠、`判断不能` なら利用条件の結論を確認できる根拠 URL と確認日

この停止結果には、候補、selector、保存済みページ資料の内容、商品値、認証情報を含めない。

### 許可

判断が `許可` のときだけ、判断記録を残した後に、後続の保存済みページ資料の読取、候補生成、検証の手順へ進める。ここで登録を行ったり、登録可能な候補を出したりしてはならない。後続の手順がまだ満たされない限り、`page-capture` への登録または既存登録の更新は行わない。

## 保存済み資料から候補を作る

この手順は、利用条件が `許可` と記録された後だけに行う。指定した保存済みページ資料を読み取り、対象ページ URL と対応するページであることを URL または資料中の識別情報から一意に確認する。確認できないときは、`ページ識別` の停止結果を返し、候補、selector、期待値、登録対象を出さない。

ページを識別できたときは、取得したい各項目について、資料に明記された値を直接読む選択規則を一つずつ探す。候補には、次のすべてをそろえる。

- ページ識別条件
- 項目名と選択規則
- 安定した人間可読の由来ラベル
- 資料から検出した未加工の期待値

期待値は選択規則がその資料から読む値との照合にだけ使う。ページ本文、HTML、画像、商品値、認証情報を判断記録または Skill の報告へ転記してはならない。

要求項目の一つでも資料から検出できない、または選択規則で直接読めないときは、候補全体を登録対象にしない。`要求項目の確認` の停止結果で、検出できなかった項目と理由、次に必要な資料または要求項目の見直しを示す。この停止結果に候補、selector、期待値、登録対象を含めない。

### 受け付ける項目

候補にできる共通項目は、名称、メーカー、型番、カテゴリ、価格、URLだけである。属性は、対象カテゴリに既に定義された `CATEGORY_ATTRIBUTES` のキーだけを受け付ける。許可する組合せは次に限る。

| 対象カテゴリ | 属性キー |
| --- | --- |
| CPU、マザーボード | `socket` |
| CPUクーラー | `supportedSockets` |
| マザーボード、メモリー | `memoryStandard` |
| マザーボード、電源 | `formFactor` |
| ケース | `supportedMotherboardFormFactors`、`supportedPowerSupplyFormFactors` |

GPU、ストレージ、ケースファンの属性、容量、定格出力、ファン寸法、未分類の属性、既存の `CaptureField` にない属性は候補に含めない。対象カテゴリに対応しない属性キー、または資料に明記されない値も、共通項目への代替や値の推測をせず、候補全体を登録対象にしない。

この段階で出す候補は未検証であり、登録、既存登録の更新、実行時型や候補編集への引渡しを行わない。保存済み資料による検証と登録の提案は後続の手順でのみ行う。

## 検証済み候補の登録と候補編集への引渡しを提案する

保存済み資料で指定項目を確認した候補だけを、`page-capture` へ登録できる候補として提案する。この提案には、追加または更新する `src/capture/site-extractors.ts` のサイトごとの登録、対象カテゴリ、ページ識別条件、項目ごとの selector、変換しない未加工の読取規則、安定した人間可読の由来ラベルを含める。汎用規則、メーカー公式ドメイン登録簿、他サイトの定義は提案の変更対象にしない。

登録提案は、`page-capture` が所有する次の実行時変更を一組として明示する。

- `SiteExtractor` の collector が `RawCandidate` を返し、`field` は既存の `CaptureField`、`rawValue` は selector が得た未加工の文字列だけにすること
- `ExtractionSource` と protocol の列挙に固定値 `site-specific` を追加し、`source` に動的なサイト名や selector を入れず、`sourceLabel` に安定した由来ラベルを入れること
- `captureSource_site_specific` の日本語・英語メッセージを追加し、既存の `captureSource_${source}` と項目由来表示で利用者に固有由来と `sourceLabel` を示すこと

固有規則は、許可ホストとページ識別条件に一致するときだけ適用する。selector が見つからない、または読取中に失敗した項目は候補を追加せず、例外を外へ出さない。その後も既存の JSON-LD、meta、構造 collector を実行して、その項目を汎用抽出へフォールバックさせる。この固有由来、失敗時の汎用フォールバック、同一項目では既存の先着規則により固有候補が選ばれることを、登録提案の検証対象に含める。

候補編集への引渡しは、`page-capture` が consume する `candidate-capture-handoff` だけを使うよう提案する。完全な handoff には、名称・メーカー・型番の元表記、取得時分類の元表記と対応する既存 `PartCategory`、そのカテゴリの `CATEGORY_ATTRIBUTES` にある属性キーごとの元表記と由来ラベル、URL、取得元種別、取得時刻、任意の価格を含める。分類が得られない場合は属性を渡さない。既存属性を扱う提案では、許可されたキーだけが属性元表記として渡り、分類・属性の元表記は候補編集で未確認のままであり、利用者が確認するまで `category` または属性の `confirmed` へ昇格しないことを検証対象に含める。

この Skill は `page-capture` の実行時型、Zod 検証、正規化、session 結果、または `project-candidate-management` の handoff 型、候補下書き、保存、確認済み値への昇格を実装・所有しない。これらの変更と実拡張での検証は各所有者へ提案するだけであり、登録提案そのものは後続の保存資料および実拡張の検証に合格するまで実行しない。

## 実拡張で登録候補を検証する

保存済み資料の検証を通った候補であっても、この段階を完了するまで登録または更新を提案してはならない。`page-capture` が所有する `e2e/capture.spec.ts` の既存入口を拡張し、ビルド済み拡張を起動して確認する。新しいテスト基盤や実サイト由来の資料は作らない。

1. 候補を追加する前に、同じ実在データを含まない fixture で既存の汎用抽出シナリオを実拡張から実行し、その安全なシナリオ識別子と結果を判断記録に控える。ページ本文、HTML、商品値、selector、認証情報は控えない。
2. 候補を加えた検証では、拡張アイコン操作を入口として、指定項目の `site-specific` 由来と安定した `sourceLabel`、`CaptureResult` と候補編集に渡る分類・属性の未確認性を確認する。属性を扱う場合は、対象カテゴリの許可キーだけが元表記として handoff へ渡り、`category` と属性の `confirmed` が設定されないことも確認する。
3. 同じ fixture で固有 selector が値を返さない状態を作り、例外を外へ出さず、その項目が JSON-LD、meta、構造 collector による既存の汎用結果へフォールバックすることを確認する。資料に明記されない項目は候補にも handoff にも加えず、推測しない。
4. `pnpm validate` を実行し、前段で記録した汎用シナリオを含む既存シナリオが維持されることを確認する。実拡張の観測、指定項目の保存資料による検証、汎用シナリオの維持のすべてに合格したときだけ、登録または更新の提案を出す。いずれかが失敗した場合は `登録結果: 未登録` として停止し、登録差分や更新提案を出さない。

fixture、E2E、実行時変更は `page-capture` の所有物である。この Skill は、実在のサイト、URL、ページ資料、商品値を作らず、登録候補ごとに上記の検証を所有者へ提案するだけにする。固定 Skill 手順の照合は `references/verification.md` に従い、実拡張 E2E で置き換えない。

## 再生成時に既存登録を保持する

再生成では、既存の検証済み登録の安全な識別子と以前の判断記録の識別子を、最初の五入力に加えて確認する。新しい保存済み資料を読む前に、初回と同じ順で利用条件を改めて判定し、許可・根拠 URL・確認日を同じ判断記録へ追記する。禁止または判断不能なら資料を読まず、候補、検証、更新を出さない。

許可時は候補生成、保存資料による指定項目の確認、候補追加前の汎用シナリオ記録、実拡張検証、`pnpm validate` を初回と同じように繰り返す。どの段階でも失敗した場合は、同じ判断記録へ `再生成日時`、`保存資料識別子`、`既存登録: 保持`、`失敗段階`、`停止理由`、`次に必要なもの`、`登録結果: 未登録` を追記する。既存登録の差分、未確認候補による置換、登録または更新の提案を出してはならない。

新しい保存資料の指定項目検証と実拡張検証がともに合格し、既存の汎用シナリオも維持された場合だけ、既存登録を更新できる候補として提案する。この提案は既存登録を直ちに置き換える操作ではない。
