# Requirements Document

## Project Description (Input)

`pc-build-planner` の取り込みエンジンは構造化メタデータ（JSON-LD の `priceCurrency`、OpenGraph の `product:price:currency`）に依存する設計であり、実装としては既に国・言語に依存しない汎用エンジンになっている。にもかかわらず UI 文言が日本語のみであるため、日本語話者以外が利用できない。実装の汎用性と提供形態が乖離している。

前提 spec `ui-message-catalog` の完了により、UI 文言は単一カタログから解決され、view とロジック層に日本語リテラルが残っていない。ただしカタログの値は日本語1言語のみである。`_locales/` は存在せず、`chrome.i18n` の利用箇所もゼロで、`side-panel.html` は `<html lang="ja">` に固定されている。

本 spec は、確定済みのキー体系の上へ英語カタログと言語解決の仕組みを載せ、利用者がサイドパネル内で表示言語を切り替えられ、その選択が次回起動時も保持される状態にする。あわせて拡張マニフェストの `name` / `description` を Chrome の表示言語に追従させ、Chrome Web Store のロケール別掲載情報を入稿できる状態にする。日本語ロケール向けの局所最適化（`円` 表記の価格パース、日本語ECサイト向けのカテゴリ推定キーワード辞書）は翻訳対象外のロケール別データ・ロジックとして明示的に位置づける。

言語切り替えの手段は自前カタログとアプリ内状態によって提供する。ブラウザの表示言語に追従するだけの仕組みでは、利用者が拡張の中で言語を選ぶことができないためである。

## Introduction

本 spec の利用者は、日本語話者と非日本語話者の双方の拡張利用者である。加えて、将来3言語目を追加する開発者と、Chrome Web Store へロケール別掲載情報を入稿するリリース担当者が二次的な利用者となる。

要件は次の4群に分かれる。

1. **アプリ内の言語体験** — 言語の切り替え、初期値の決定、選択の保持（要件1〜3）
2. **翻訳データの完備** — 英語カタログの網羅、数量を含む文の英語表現（要件4）
3. **アプリ外の国際化** — 文書の言語属性、拡張マニフェストとストア掲載（要件5、要件6）
4. **境界の明示と検証** — 翻訳対象外データの隔離、検証フローと配布物、将来の言語追加（要件7〜9）

上位の制約として、言語の切り替えはブラウザの再起動や実行環境のロケール設定の変更を必要としないこと、および言語設定が利用者のドメインデータ（プロジェクト・候補・現在構成）へ混入しないことを置く。

## Boundary Context

- **In scope**:
  - 表示言語として日本語と英語を選べること、および選択の即時反映
  - 表示言語の初期値決定（保存された選択の有無、ブラウザの表示言語の反映）
  - 表示言語の選択の保持（拡張の再起動をまたぐ）
  - 英語の表示文言一式。`ui-message-catalog` が確定させたキー体系をそのまま用いる
  - 数量を含む文の英語表現（復元完了の件数表示を含む）
  - サイドパネル内の言語切り替え操作面
  - サイドパネル文書の言語属性が現在の表示言語と一致すること
  - 拡張マニフェストの `name` / `description` が Chrome の表示言語に追従すること、および Chrome Web Store のロケール別掲載情報を入稿可能な状態にすること
  - `円` 表記の価格パースと日本語カテゴリ推定キーワード辞書を、翻訳対象外のロケール別データ・ロジックとして明示すること
  - 既存のマニフェスト構造検証と配布物検証が新しい構造を受け入れること
  - 英語UIの E2E 検証
- **Out of scope**:
  - UI 文言のカタログ化そのもの、スタイルおよび E2E ロケータの文言非依存化、view からの日本語リテラル除去（すべて `ui-message-catalog` が所有し、本 spec の着手前に完了している）
  - 日本語・英語以外の言語の翻訳データ
  - カテゴリ推定キーワード辞書の多言語化。英語ECサイト向けのカテゴリ推定は別の課題であり、本 spec は日本語辞書を隔離するところまでを行う
  - ロケール別の日付・数値・通貨の表示整形
  - 通貨の自動換算、為替レート取得
  - Chrome Web Store の詳細説明・スクリーンショットの英語版作成（ダッシュボードでの入稿作業）
  - 商品取り込みの抽出・正規化の振る舞いの変更、バックアップ形式および復元の振る舞いの変更
  - 表示文言の文面改善および UI の再デザイン
- **Adjacent expectations**:
  - `ui-message-catalog` が確定させたキー集合・パラメータ・参照経路を入力として受け取り、変更しない。英語対応のためにキーを追加・改称する必要が生じた場合も、参照側の解決経路の形は変えない
  - アプリケーションシェルは画面合成と機能の搭載・解放のライフサイクルを所有し続ける。言語切り替え操作面はその所有関係の中へ収まる
  - 利用者データの保存・復元の唯一の権限は既存の保存基盤が持ち続ける。表示言語の設定は利用者のドメインデータではなく、バックアップ・復元の対象にならない
  - 各機能の受け入れ条件は据え置かれる。表示言語が変わっても、操作結果・保存内容・互換性判定は変化しない
  - リリース作業は既存の手順をそのまま用いる。配布物に新しい資産が加わることだけが差分となる

## Requirements

### Requirement 1: サイドパネル内での表示言語の切り替え

**Objective:** As a 拡張の利用者, I want サイドパネルの中で表示言語を日本語と英語から選べること, so that ブラウザや OS の設定を変えずに自分が読める言語で拡張を使える

#### Acceptance Criteria

1. The サイドパネル shall 日本語と英語のいずれかを表示言語として選択できる操作面を、どの機能を表示している状態でも提供する。
2. When 利用者が表示言語を切り替えた場合, the サイドパネル shall 表示中の画面の全ての文言を、ブラウザの再読み込みや拡張の再起動を必要とせずに選択後の言語で表示する。
3. When 利用者が表示言語を切り替えた場合, the サイドパネル shall 表示中の機能、選択中の項目、入力途中の内容、および画面のスクロール位置を保持する。
4. The サイドパネル shall 表示言語の切り替えによって、保存済みのプロジェクト・候補・現在構成の内容および互換性判定の結果を変化させない。
5. While 保守中またはエラーを表示している状態, the サイドパネル shall 表示言語の切り替え操作を引き続き受け付ける。
6. The 言語切り替えの操作面 shall 選択肢を各言語自身の名称で表示し、現在選択されている言語を利用者が判別できる形で示す。

### Requirement 2: 表示言語の初期値決定

**Objective:** As a 拡張の利用者, I want 初回利用時に妥当な言語で拡張が表示されること, so that 最初から言語を設定し直さなくても内容を理解できる

#### Acceptance Criteria

1. When 保存された表示言語の選択が存在する状態で拡張を開いた場合, the サイドパネル shall その言語で表示する。
2. If 保存された表示言語の選択が存在しない, then the サイドパネル shall ブラウザの表示言語を対応言語へ対応付けた結果を初期値として用いる。
3. If ブラウザの表示言語が日本語である, then the サイドパネル shall 地域差（`ja-JP` などの地域付き表記を含む）にかかわらず日本語を初期値として用いる。
4. If ブラウザの表示言語が対応言語のいずれにも対応付けられない, then the サイドパネル shall 英語を初期値として用いる。
5. If 保存された表示言語の選択が読み取れない、または対応言語として解釈できない値である, then the サイドパネル shall 保存値が存在しない場合と同じ手順で初期値を決定し、起動を失敗させない。
6. The サイドパネル shall 初期値の決定を、利用者が表示言語を明示的に選択した後は行わない。

### Requirement 3: 表示言語の保持とドメインデータからの分離

**Objective:** As a 拡張の利用者, I want 一度選んだ表示言語が次に拡張を開いたときも保たれること, so that 起動のたびに設定し直さずに済む

#### Acceptance Criteria

1. When 利用者が表示言語を選択した場合, the 拡張 shall その選択を、拡張の再起動およびブラウザの再起動をまたいで保持する。
2. The 拡張 shall 表示言語の設定を、バックアップファイルへ出力する利用者データに含めない。
3. When 利用者がバックアップから復元した場合, the サイドパネル shall 復元の前後で表示言語を変化させない。
4. The 拡張 shall 表示言語の設定の読み書きによって、プロジェクト・候補・現在構成の保存内容および保存の整合性に影響を与えない。
5. If 表示言語の設定を保存できなかった, then the サイドパネル shall その回の表示は選択された言語のまま継続し、利用者の操作を中断させない。
6. The 拡張 shall 表示言語の設定によって、利用者データの保存容量の監視前提を崩さない大きさに設定を留める。

### Requirement 4: 英語表示文言の完備

**Objective:** As a 非日本語話者の利用者, I want 全ての画面・状態・エラー表示が英語で読めること, so that 日本語が読めなくても拡張の機能を一通り使える

#### Acceptance Criteria

1. The メッセージカタログ shall 日本語カタログと英語カタログが同一のキー集合を持つことを保証し、いずれかにキーの不足がある場合は検証フローが型検査の段階で失敗する。
2. The メッセージカタログ shall 各キーが受け取るパラメータの名前と個数を言語間で一致させる。
3. While 表示言語が英語である状態, the サイドパネル shall ナビゲーションラベル、画面本文、入力欄の補助表示、利用者が知覚しうる要素の説明ラベル、確認・完了・失敗の各通知を英語で表示する。
4. Where 件数を含む文が存在する場合, the サイドパネル shall 英語表示時に件数に応じた適切な単複表現を用いる。
5. The サイドパネル shall 復元完了の通知において、複数種類の件数を含む文を、英語として自然に読める1つの文として表示する。
6. The サイドパネル shall パーツカテゴリ名を含む共有語彙を、機能をまたいで同一の英語表記で表示する。
7. The サイドパネル shall 利用者が入力した名称・取得元・ファイル位置などの外部由来文字列を、表示言語にかかわらず翻訳せずそのまま表示する。

### Requirement 5: 文書の言語属性

**Objective:** As a 支援技術を利用する利用者, I want 表示中の言語が文書の言語として正しく宣言されていること, so that 読み上げが正しい言語規則で行われる

#### Acceptance Criteria

1. The サイドパネル shall 文書の言語宣言を、現在の表示言語と一致させる。
2. When 利用者が表示言語を切り替えた場合, the サイドパネル shall 文書の言語宣言を切り替え後の言語へ更新する。
3. The サイドパネル shall 文書の言語宣言を、特定の言語へ固定した静的な値として保持しない。

### Requirement 6: 拡張マニフェストとストア掲載の国際化

**Objective:** As a リリース担当者, I want 拡張の名称と説明が Chrome の表示言語に応じて切り替わること, so that Chrome Web Store へロケール別の掲載情報を入稿でき、拡張一覧でも利用者の言語で表示される

#### Acceptance Criteria

1. The 拡張 shall 拡張の名称と説明を、Chrome の表示言語に応じて日本語と英語で切り替えて提供する。
2. The 拡張 shall 最終フォールバック先となる既定ロケールを宣言し、そのロケールが名称と説明の全項目を欠落なく持つ。
3. If 既定ロケール以外のロケールに未提供の項目がある, then the 拡張 shall 既定ロケールの値へフォールバックし、読み込みに失敗しない。
4. The 拡張 shall ロケール別掲載情報の仕組みを、拡張の名称と説明の範囲に限って用い、サイドパネル内の表示文言の解決には用いない。
5. When 拡張を読み込んだ場合, the 拡張 shall 既定ロケールの宣言とロケール別資産の実在が整合しない状態にならない。
6. The 拡張 shall 宣言する権限、最低対応バージョン、コンテンツセキュリティポリシーを本変更によって変更しない。

### Requirement 7: 翻訳対象外のロケール固有データ・ロジックの明示

**Objective:** As a 拡張の開発者, I want 日本語ロケール向けの局所最適化が翻訳対象の文言と構造上・文書上で区別されていること, so that 国際化の作業がそれらを誤って翻訳・削除・多言語化しない

#### Acceptance Criteria

1. The 拡張 shall `円` 表記の価格解釈と日本語カテゴリ推定キーワードを、表示文言ではなく日本語ロケール向けの取り込み支援データ・ロジックとして識別できる形で保持する。
2. The 拡張 shall 上記のデータ・ロジックについて、翻訳対象外である理由と、他ロケールでの動作を妨げないことを文書上で明示する。
3. The 商品取り込み shall 本 spec の前後で、価格・通貨・カテゴリ推定の抽出結果を変化させない。
4. The 商品取り込み shall 表示言語の選択にかかわらず、同一の入力に対して同一の抽出結果を返す。
5. If 日本語ロケール向けデータが表示文言として扱われた, then the 検証フロー shall 失敗する。

### Requirement 8: 検証と配布物への反映

**Objective:** As a 拡張の開発者, I want 英語UIと国際化された配布物が既存の検証フローの中で自動的に確認されること, so that 実行環境の言語設定に依存する手作業の確認を持ち込まずに回帰を防げる

#### Acceptance Criteria

1. The E2E 検証 shall 英語表示の画面を、ブラウザの再起動、実行環境のロケール環境変数の操作、およびブラウザ起動オプションの変更を必要とせずに検証する。
2. The E2E 検証 shall 英語表示の検証を、拡張内の言語切り替え操作を通じて行う。
3. The 検証フロー shall ブラウザの表示言語から初期値を決定する手順を、実ブラウザの起動を伴わない検証で確認する。
4. When 配布物を生成した場合, the 拡張 shall ロケール別資産を配布物および配布用パッケージへ欠落なく含める。
5. The 検証フロー shall 変更後のマニフェスト構造を受け入れ、既存の権限・セキュリティに関する検査を引き続き有効に保つ。
6. The 検証フロー shall 型検査、静的検査、公開境界検査、フィクスチャ検査、文言検査、最終ビルドゲート、単体・統合テスト、E2E の全てを本 spec 完了時点で成功させる。

### Requirement 9: 将来の言語追加への拡張性

**Objective:** As a 将来の言語を追加する開発者, I want 3言語目以降を既存の参照箇所を触らずに追加できること, so that 言語追加の作業量がカタログの追加に閉じる

#### Acceptance Criteria

1. The メッセージカタログ shall 言語を追加する際に、表示文言を参照している画面側の記述の変更を要求しない。
2. If 追加した言語のカタログにキーの不足がある, then the 検証フロー shall 型検査の段階で失敗する。
3. The 拡張 shall 対応言語の集合を単一の定義から導出し、対応言語の追加が選択肢・初期値決定・保存値の解釈へ一貫して反映されるようにする。
4. The 本 spec shall 日本語・英語以外の翻訳データを提供しない。
5. The 拡張 shall 表示文言の解決に実行時の動的読み込みを用いず、翻訳データを配布物へ静的に含める。
