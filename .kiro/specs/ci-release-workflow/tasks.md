# Implementation Plan

## 1. 基盤: 検証セットの分解とバージョン解決

- [x] 1.1 検証セットをE2E込みとE2E抜きへ分解する
  - 既存の全検証（型検査2種、静的検査、公開境界検査、fixture検査、最終build gate、test）を逐次実行するE2E抜きの検証セットを新設する
  - 従来の完全検証を「E2E抜きの検証セット + Playwright E2E」の合成として再定義し、検査内容が分解前後で変わらないことを保つ
  - 各検証が何を検査するかには手を入れない。呼び出しの組み替えのみを行う
  - 開発基盤のsmoke testを更新し、完全検証がE2E抜きセットとE2Eの合成であること、E2E抜きセットにE2Eが含まれないことを検査する
  - 完了状態: クリーンな作業ツリーでE2E抜きの検証セットを実行して成功し、更新後のsmoke testを含む全testが通る
  - _Requirements: 2.3, 2.4, 2.5_
  - _Boundary: package.json scripts_

- [x] 1.2 (P) リリースバージョンの解決と整合検証を実装する
  - manifestのversionをリリース対象バージョンの正とし、そこからタグ名とzipファイル名を導出する単一の情報源を用意する
  - manifestとpackage定義のversionが一致しない場合、双方の実測値を含むメッセージで失敗させる
  - versionが未定義または空の場合も明示的に失敗させる
  - GitHub Actions固有の環境変数を参照せず、CLI実行時はキーと値の行を標準出力へ書くのみとする
  - 導出規則（タグ名・zip名の形式）と不一致検出の単体testを追加する
  - 完了状態: 現行のmanifestに対して実行すると version・tag・zip名の3値が出力され、versionを意図的にずらした入力では不一致を報告して失敗する
  - _Requirements: 3.3, 4.4, 4.5, 4.6_
  - _Boundary: release-version script_

## 2. コア: パッケージングとリリースノート生成

- [x] 2.1 (P) 配布用zipの生成を実装する
  - build成果物のうち配布対象のみをステージング領域へ複製し、ドットで始まるファイル（ビルド内部マーカーを含む）を除外する
  - ステージング結果に対して既存の生成物検査を再実行し、検査に失敗した場合はzipを生成しない
  - ステージング領域の中身を圧縮し、展開結果の最上位にmanifestが来る構造にする
  - zipファイル名はタスク1.2で定めた導出規則から受け取る。名前の形式をここで再定義しない
  - 実行のたびにステージング領域と既存zipを削除してから作り直す
  - 圧縮には新規の依存パッケージを追加せず、実行環境の標準手段を用いる。起動失敗・非ゼロ終了は必要なコマンド名を含むメッセージで失敗させる
  - build後にパッケージングを行う実行コマンドを用意し、zip出力先を追跡対象外にする
  - ステージング除外規則、最上位構造、成果物欠損時の失敗、再実行時の残骸非持ち越しを検証するtestを追加する
  - 完了状態: build済みの状態でパッケージングコマンドを実行するとversionを含む名前のzipが1つ生成され、その中身に内部マーカーが含まれずmanifestが最上位に存在する
  - _Requirements: 3.1, 3.2, 3.4, 3.5, 3.6_
  - _Depends: 1.2_
  - _Boundary: package script_

- [x] 2.2 (P) リリースノートの整形を実装する
  - closed issueの一覧（番号・タイトル・URL・label）を標準入力から受け取り、Markdownのリリースノート本文を返す純関数として実装する。GitHub APIへは直接アクセスしない
  - labelの優先順位表（新機能・改善 → 不具合修正 → ドキュメント）で最初に一致したグループへ各issueを分類し、1つのissueが複数グループへ重複掲載されないようにする
  - 優先順位表のいずれにも該当しないlabelのみを持つissue、およびlabel未付与のissueを既定グループへ分類し、リリースノートから欠落させない
  - 各issueを番号とタイトルつきで、当該issueへ辿れる形式で列挙する。該当issueが0件のグループは出力しない
  - 入力が空、または必須フィールドを欠く要素を含む場合は失敗させる
  - グルーピング規則、未知labelとlabel未付与の扱い、入力件数と出力件数の一致、空入力時の失敗を検証する単体testを追加する
  - 完了状態: 複数labelを含むissue一覧を渡すと見出し単位にグルーピングされたMarkdownが出力され、入力した全issueがちょうど1回ずつ出現する
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5_
  - _Boundary: release-notes script_

## 3. 統合: ワークフローの構築

- [x] 3.1 (P) 検証CIワークフローを構築する
  - mainへのpush、mainを対象とするpull request、および手動起動で動作させ、ドキュメント・spec・Markdownのみの変更では起動しないよう除外条件をpushとpull requestの双方へ指定する
  - 同一参照に対する先行実行を打ち切る同時実行制御を設定する
  - ツール管理定義に固定されたNode.jsとpnpmのバージョンをキャッシュ有効で再現し、lockfile整合を強制する依存インストールを行う
  - タスク1.1で用意したE2E抜きの検証セットを呼び出すだけの構成とし、ワークフロー側に検証ロジックを持たせない
  - 権限を読み取りのみに限定し、各ステップに失敗段階が判別できる名前を付ける
  - 完了状態: mainへのpushで当該ワークフローが起動して成功し、GitHub上の実行ログからステップ単位の成否が確認できる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 2.1, 2.2, 2.4, 2.6, 7.6_
  - _Depends: 1.1_
  - _Boundary: ci workflow_

- [x] 3.2 (P) リリースワークフローの前提ゲートを構築する
  - 手動起動のみで動作するワークフローを新設し、pushやpull requestでは起動しないようにする
  - 書き込み権限をリリース作成とマイルストーン更新に必要な範囲へ限定する
  - タスク1.2のバージョン解決を呼び出してversionとタグ名を確定し、version不一致をここで失敗させる
  - 同名のタグまたはリリースが既に存在する場合に失敗させる
  - タグ名と同一titleのマイルストーンを特定し、不在・既にclosed・open issueが1件以上・closed issueが0件のいずれかで失敗させる。未完了issueは番号とタイトルの一覧としてログへ出す
  - open/closed issueの件数判定にはpull requestを含まないissue一覧を用い、マイルストーンの集計値を根拠にしない
  - これらのゲートを完全検証より前に配置し、失敗時に副作用が一切残らない状態を保つ
  - 完了状態: open issueが残るマイルストーンに対して手動起動すると、完全検証へ到達する前に未完了issue一覧つきで失敗する
  - _Requirements: 4.1, 4.4, 4.5, 4.6, 4.7, 5.1, 5.2, 5.3, 5.4, 5.5, 6.5, 7.5_
  - _Depends: 1.2_
  - _Boundary: release workflow_

- [x] 3.3 リリースワークフローの検証・公開・完了処理を構築する
  - E2E実行に必要なブラウザを取得したうえで、E2Eを含む完全検証を単一ジョブ内の単一ステップとして実行する。検証をジョブ分割しない
  - 完全検証が失敗した場合、リリース作成もマイルストーン更新も行わずに終了する
  - 検証通過後にタスク2.1のパッケージングを実行し、生成zipをワークフロー成果物としてアップロードする。アップロードはリリース作成より前に配置し、後続が失敗しても回収可能にする
  - マイルストーン配下のclosed issue一覧を取得してタスク2.2の整形へ渡し、リリースノート本文を生成する
  - タグを付与したリリースを作成してzipを添付し、成功した場合にのみ対象マイルストーンをcloseする
  - マイルストーンcloseのみが失敗した場合、リリースは公開済みであり手動closeが必要である旨をログへ出す
  - 各ステップに失敗段階が判別できる名前を付ける
  - 完了状態: 前提を満たしたマイルストーンに対して手動起動すると、リリース作成・zip添付・成果物アップロード・マイルストーンcloseが完了する
  - _Requirements: 4.2, 4.3, 7.1, 7.2, 7.3, 7.4, 7.6_
  - _Depends: 2.1, 2.2, 3.2_
  - _Boundary: release workflow_
