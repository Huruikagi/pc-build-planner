# デリバリー方針

各フェーズ（requirements / design / review / validation）が「どこまでやったら十分か」を決める文書。品質基準そのものは `tech.md`・`testing.md`・`security.md` が定義する。本書はその**適用の深さと停止条件**を定める。

上限を定めないと、各フェーズは「思いつく限り厳密に」へ倒れる。v0.x では、それは品質ではなく停滞として扱う。

## v0.x のフェーズ宣言

**v0.x は MVP フェーズであり、目的は網羅品質ではなくハッピーパスの到達である。**

達成すべきは `product.md` の「コア能力」1〜5 が、ユーザーの通常操作で端から端まで通ること。理論上の入力空間の網羅、将来の拡張余地の先取り、細部の最適化は v0.x の目的ではない。

この宣言は品質の放棄ではない。**壊れると取り返しがつかないもの**へ厳しさを集中させ、それ以外を後回しにする優先順位付けである。

## ブロックする条件（Critical / Important のまま扱う）

以下は v0.x でも受け入れ前の修正を必須とする。

- **承認済み受け入れ基準の未達**。通常操作で spec の受け入れ基準を満たさない。
- **コア能力のハッピーパスが通らない**。`product.md` のコア能力 1〜5 が通常操作で端から端まで到達しない。v0.x の目的そのものであり、他のどの分類にも当たらない機能不全をここで拾う。
- **データの損失・破損**。永続化、migration、参照修復、atomic replacement の誤りを含む。
- **バックアップ・復元の非可逆な失敗**。ユーザーが自力で復旧できなくなる経路。
- `security.md` の違反。未信頼文字列の扱い、CSP、権限境界を含む。
- **承認済み spec からの無断逸脱**。範囲外の挙動追加、承認なしの契約変更。
- **検証が無効であること**。実装を削除・破壊してもテストが落ちない、evidence が提示されていない、RED が主張のみで示されていない。
- **公開境界の違反**。`structure.md` が定める `public.ts` / `worker-public.ts` / `feature-contribution.ts` 以外からの内部 import。

## ブロックしない条件（Suggestion へ落として記録し、先へ進む）

以下は指摘としては妥当でも、v0.x では受け入れを止めない。`Suggestion` に分類し、後述の受け皿へ記録した上で完了扱いにしてよい。

- 通常操作で到達しない稀な入力・異常系の分岐網羅
- UI 文言の細部、エラーメッセージの粒度
- パフォーマンス最適化（実測された問題がない限り）
- 将来の機能拡張を見越した抽象化・拡張点の用意
- 型の厳密化（動作が正しく、境界が守られている場合）
- 命名・構造の好みに属するリファクタリング

### 他 steering との優先関係

**本書の非ブロック例は、security、データ保全、公開境界、承認済み受け入れ基準、アクセシビリティ契約、および他の steering で明示的に必須とされた検証を上書きしない。** 衝突した場合は厳しい側が優先する。

具体的には、次は上記リストに文言上該当して見えても非ブロックにしない。

- 「UI 文言の細部」に、誤操作を招く表示、アクセシビリティ、日英 UI 契約の違反は含めない。
- 「稀な入力の分岐網羅」に、`tech.md` が回帰対象としている破損入力、schema 移行、容量不足、競合、原子的置換、maintenance fencing、navigation、feature 障害分離は含めない。

## requirements フェーズの上限

レビューが重くなる原因の多くは、requirements が最初から細かすぎることにある。上流で絞る。

- EARS の異常系は**ユーザーが通常操作で到達しうる失敗**に限る。理論上可能な入力の全列挙はしない。ただし前節の優先関係が適用され、`tech.md` の回帰対象はこの上限で削らない。
- 一つの spec の受け入れ基準は、コア能力への寄与で説明できるものに限る。
- 「将来 X になったとき」を前提にした要件を v0.x の spec へ書かない。ロードマップ側へ置く。

## Suggestion の受け皿

**Suggestion に落とした指摘は捨てない。** 受け皿がないと、レビュアーは消えて困る指摘をすべて `Important` に上げるしかなくなり、本書は機能しない。

先送り一覧は `docs/deferred-v0.x.md` とする。運用は次のとおり。

- レビュアーは `Suggestion` を review 出力の `DEFERRED` 欄に列挙する。レビュアーは読み取り専用なので、ファイルへは書かない。
- 制御側（`kiro-impl`）が APPROVED 時に `DEFERRED` 欄を `docs/deferred-v0.x.md` へ追記し、そのコミットへ含める。
- 追記の完了によって完了扱いにできるのは、**その指摘への処置**だけである。実装タスク自体の完了可否は、従来どおり受け入れ基準とレビュー判定で決まる。
- v1.0 へ向けた再検討時に、この一覧を入力とする。

## この方針の失効

v0.x の間に限る。v1.0 の spec 着手時点で本書を見直し、ブロック条件を広げるか、本書自体を撤去する。
