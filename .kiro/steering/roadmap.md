# ロードマップ

## 概要
日本の自作PCユーザーが、パーツを探し、比較し、構成を保存し、将来のアップグレードを検討できるWebサービスを構築する。価格比較サイトの代替ではなく、構成計画を中心に据える。

初期は低コストなCloudflare基盤上にPWAとして提供し、URL貼り付けと対応環境での共有ターゲットからパーツ候補を取り込む。Chrome拡張などの将来クライアントも同じ取り込みAPIへ接続できる構造にする。

## アプローチ決定
- **採用**: Cloudflareフルスタック。TypeScript PWA、WorkersとStatic Assets、D1、Queues、必要時のみBrowser Runを利用する。
- **理由**: 初期固定費を抑えながら、Web配信、構造化データ、非同期URL解析を同一基盤で提供できる。初期の検索は日本語全文検索より、メーカー、Socket、DDR世代、寸法などの構造化条件が中心である。
- **不採用案**: Next.js + Vercel + Supabaseは関係モデルに強いが公開運用の固定費と解析ワーカー分離が早期に必要。Firebase / Google Cloudはモバイル連携に強いが、関係データの非正規化と検索基盤の追加が必要。

## スコープ
- **対象**: Web/PWA基盤、パーツカタログ、URLからの登録候補作成、検索・絞り込み・比較、構成の作成・保存・編集・複製・比較、差分ベースのアップグレード検討。
- **対象外**: 価格比較サイト化、販売店横断クローリング、価格履歴、公開共有URL、SNS機能、完全自動登録、互換性・ボトルネック・電力・物理干渉の自動判定、ネイティブアプリ、Chrome拡張本体。

## 制約
- 主対象は日本ユーザーとし、UIと成果物の既定言語を日本語とする。
- PWA Share Targetは限定対応のため、通常のURL貼り付けを常に提供する。
- 任意URL取得ではSSRF対策、リダイレクト再検証、サイズ・時間制限、取得物の非信頼化を必須とする。
- Browser Runはbot対策を回避できないため、取得失敗と手動入力・確認を正式なフローとして扱う。
- Queuesはat-least-once配信のため、取り込みジョブと登録処理を冪等にする。
- D1固有処理、URL抽出、検索索引を境界の内側へ隔離し、容量・並行性・検索品質が限界に達した場合に移行できるようにする。
- サイトごとの利用規約、robots、著作権、アクセス頻度を確認し、許可された範囲でのみ解析する。

## 境界戦略
- **分割理由**: 正規データを所有するカタログ、未確定データを扱う取り込み、読み取り中心の検索比較、ユーザー状態を持つ構成、差分シナリオを持つアップグレードを分離し、独立した仕様化と検証を可能にする。
- **共有境界の注意点**: 正規化済みパーツID、カテゴリ別属性、出典URL、構成スロット、取り込み状態を共通契約とする。基盤仕様を肥大化させず、各ドメインの所有権を明確にする。

## 仕様（依存順）
- [ ] platform-foundation -- 日本語PWA、Cloudflare実行基盤、共通ID、永続化・ジョブ・認証方針の最小基盤。依存: なし
- [ ] parts-catalog -- カテゴリ別属性を持つ正規化パーツと出典情報の管理。依存: platform-foundation
- [ ] part-ingestion -- URL受付、非同期解析、重複検出、候補確認からカタログ登録まで。依存: platform-foundation, parts-catalog
- [ ] part-discovery-comparison -- カテゴリ別検索・絞り込みと複数パーツ比較。依存: parts-catalog
- [ ] build-management -- パーツ選択による構成作成、保存、編集、複製、構成比較。依存: parts-catalog, part-discovery-comparison
- [ ] upgrade-planning -- 保存済み構成を基準にした部分差し替えと差分比較。依存: build-management, part-discovery-comparison
